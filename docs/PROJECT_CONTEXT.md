# プロジェクトコンテキスト

この文書は **Cursor / Codex / 人間** が共通で読む前提です。設計・運用・文体の根拠をここに集約し、ツール間で認識がズレないようにします。

---

## プロジェクト概要

本プロジェクトは **X（旧Twitter）向けの自動運用システム** を中心とした開発・運用リポジトリです。複数の運用アカウントに対し、投稿生成・画像生成・スケジュール実行などを行い、一貫した品質とコスト（API・運用リスク）を管理することを目的とします。

**なぜこの整理が必要か:** GUI の選択値と実際に呼ばれる API が一致しないと、意図しない課金・レート制限・投稿トーンの崩壊につながる。コンテキストをコード外にも明示し、レビューと自動化の双方で参照できるようにする。

---

## システムの位置づけ

- **X 自動運用システム:** 人が毎回手動でプロンプトを貼らなくても、ルールに沿って投稿・図解・検証が回ることを目指す。
- **マルチアカウント:** アカウントごとに役割・文体・画像方針が異なるため、「共通エンジン + アカウント別ポリシー」で考える。
- **共有前提の開発運用:** 作業結果は `reports/latest_report.md` に残し、commit / GitHub push / URL 共有までを完了条件にする。詳細は `DEVELOPMENT_RULES.md` を正とする。

## 各アカウントの役割

### yokaze_daily（夜風）

- **役割:** 夜の時間帯に寄り添う短文・本音寄りの投稿。読者の感情の言語化を手伝うポジション。
- **トーン:** お兄さん感、過剰に整えた文学調は避ける（詳細は `PROMPT_HISTORY.md`）。

### ai_side_business（旧 ai_pickup）

- **役割:** 非エンジニアが、AI 時代に仕事を奪われる側ではなく、ChatGPT・Claude・Gemini・Codex などを使って自分の仕事を軽くし、業務改善できる人材を目指す実践発信。
- **トーン:** 成功者や専門家として上から教えない。怪しい副業感、簡単に稼げる系、AI ニュース紹介だけ、ツール紹介だけを避ける。実際の作業改善・業務分解・仕組み化に寄せる。
- **実践ツール:** 投稿者自身の現在の実践は Cursor ではなく **Codex** を優先して書く。

### new_account_daily

- **役割:** 新規アカウントの育成・デイリー投稿のテンプレ運用。夜風・AI 副業のどちらに寄せるかは運用方針で決め、**設定とプロンプトをセットで**管理する。

## 夜風アカウントの方向性（yokaze_daily）

| 方針 | 意図 |
|------|------|
| **夜に寄り添う** | 深夜帯の孤独感・疲れに対し、説教ではなく隣にいる感覚を出す。 |

| 方針 | 意図 |
|------|------|

## 現在の主要問題（技術・運用）

### 1. GUI 設定と内部処理の不一致

- **現象:** 画面上で選んだ Provider / モデル / 機能が、実際の HTTP クライアントや関数呼び出しと一致しない可能性がある。
- **リスク:** 意図しない課金、別モデルの出力で文体が崩れる、デバッグ不能。
- **方針:** 設定値は **実行時に一元的に解決**し、ログと突き合わせ可能にする（詳細は `DEVELOPMENT_RULES.md`）。

### 2. Gemini 固定呼び出し疑惑

- **現象:** UI では OpenAI を選んでいるつもりが、実装のデフォルトや分岐ミスで Gemini だけが呼ばれている疑い。
- **リスク:** コスト構造の想定外、利用規約・データ取り扱いの前提がズレる、混線時の品質差。
- **方針:** **Provider 切替は単一の設定ソース**から行い、呼び出し直前で必ずログに残す。

## 重要設定項目

実装形態に依存するが、少なくとも次を **アカウント別・環境別** に固定して管理する。

- **LLM Provider:** OpenAI / Google Gemini（その他を足す場合はここに追記）
- **モデル名:** テキスト用・画像用を分けて記載
- **画像生成の有無・リトライ上限**
- **API キー・エンドポイント**（秘密情報はリポジトリに直書きしない）
- **アカウント ID と上記の対応表**

**なぜ:** 設定が分散していると「どのファイルが真実か」が曖昧になり、Codex が別ブランチを読んでも判断できない。

---

## 使用 Provider（前提）

- **OpenAI:** テキスト・画像 API 等、プロジェクトで採用している範囲に合わせて利用。
- **Google Gemini:** 同上。

実際に有効な SDK・エンドポイント名はコードと `.env.example`（あれば）を正とし、本ファイルは **運用上の意味** を記す。

---

## OpenAI / Gemini 切替構造（設計原則）

1. **単一の設定解決レイヤ**  
   GUI →（保存）→ 設定ストア → **解決関数** → クライアント生成。GUI が直接クライアントを new しない。

2. **Provider ごとにファクトリまたはアダプタ**  
   OpenAI と Gemini でシグネチャが違う部分はインターフェースの裏に閉じ、呼び出し側は「テキスト生成」「画像生成」など用途単位で呼ぶ。

3. **ログで追跡可能**  
   各リクエスト前に `provider` / `model` / `called_function`（またはメソッド名）を出す（`DEVELOPMENT_RULES.md` と一致）。

4. **混線禁止**  
   1 リクエストのライフサイクル中に Provider をすり替えない。フォールバックが必要なら明示的なポリシーとログを残す。

## ドキュメントの更新ルール

重要な設計変更・運用変更・文体・画像方針・バグ修正があったら、次を更新する。

- プロジェクトの前提・問題意識 → **本ファイル**
- 開発プロセス・API・ログ・テスト → **`DEVELOPMENT_RULES.md`**
- 文体・プロンプト・過去の教訓 → **`PROMPT_HISTORY.md`**
- 重大バグ・Provider 混線・API 暴走・誤生成の記録 → **`BUG_HISTORY.md`**
- アカウント別の世界観・文体・画像・禁止事項の固定 → **`ACCOUNT_STYLE_GUIDE.md`**
- 作業結果・調査詳細・ChatGPT 共有用メモ → **`reports/latest_report.md`**（必要に応じて時刻付き report も作成）

情報を Cursor だけのチャットに閉じないこと。
