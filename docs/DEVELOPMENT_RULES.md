# 開発ルール

AI アシスタント（Cursor / Codex）と人間開発者が **同じ安全基準とデバッグ可能性** を共有するためのルールです。理由も併記します。

---

## 1. ユーザー許可なしで実 API を呼ばない

- **ルール:** 本番キーを使った外部 API（OpenAI / Gemini / X API 等）の呼び出しは、ユーザーが明示したとき、または「最終確認」として合意したときに限定する。
- **なぜ:** 課金・レート制限・アカウント凍結・意図しない投稿のリスクを避ける。エージェントの自律実行がコスト暴走しやすいため。

---

## 2. 通常テストはモックで行う

- **ルール:** ユニットテスト・結合テストのデフォルトは、HTTP クライアントや SDK をモック／スタブに差し替える。
- **なぜ:** CI の再現性、API 費用の節約、レート制限によるフレーク回避。

---

## 3. GUI 設定と内部処理の一致を必ず確認する

- **ルール:** 設定画面やコンフィグファイルを変更したら、**実際に呼ばれるコードパス**（分岐・デフォルト値・キャッシュ）を追い、期待 Provider / モデルで動くことを確認する。
- **なぜ:** 「画面上は A、実行時は B」が最も多い不具合の種。文体・コスト・規約の前提がすべて崩れる。

---

## 4. ログに provider / model / called function を出す

- **ルール:** 外部モデルや画像生成を呼ぶ直前（または直後）に、少なくとも次を構造化ログで残す。  
  - `provider`（例: `openai`, `gemini`）  
  - `model`（API に渡すモデル ID）  
  - `called_function`（例: `generate_post_text`, `create_diagram_image`）
- **なぜ:** 事後の監査と「Gemini 固定疑惑」の否定・特定に必須。サポートや自分自身のデバッグ時間を削減する。

---

## 5. GUI 設定値と実処理が一致しない場合はエラーにする

- **ルール:** 解決した設定と実際にインスタンス化したクライアントの Provider / モデルが食い違う場合は、**黙って続行せず** 例外またはフェイルセーフ停止にする（本番ではユーザー向けメッセージ + 詳細はログ）。
- **なぜ:** 誤投稿・誤課金は「失敗して気づく」より「起動時に止まる」方が損害が小さい。

---

## 6. 修正後の報告内容

変更を出す側（人間・AI）は、PR または報告に最低限次を含める。

- **原因:** 何が起きていたか（再現条件があれば記載）
- **影響範囲:** 触れたモジュール、アカウント別の挙動の変化
- **テスト結果:** 実行したテスト名、モック／実 API の別

**なぜ:** Codex が別セッションで読んでも、レビュー負荷と手戻りを減らせる。

---

## 7. 実 API は最終確認時だけ使う

- **ルール:** リグレッションの大半はモックで担保し、マージ前やリリース前に限って、ユーザー合意のもと実 API でスポット確認する。
- **なぜ:** コストと安定性のバランス。実 API に依存したテストばかりにすると CI が不安定になる。

---

## 8. API 節約を重視する

- **ルール:** 不要な再生成を避ける。キャッシュ可能な中間成果物（プロンプトハッシュ、応答の短いメタデータ）は方針に沿って再利用を検討する。デバッグ時も `max_tokens` 等を無暗に大きくしない。
- **なぜ:** 運用コストが積み上がり、レート制限で本番が止まる。

---

## 9. 画像生成リトライの乱発禁止

- **ルール:** リトライは上限回数・指数バックオフ・同一プロンプトの連打禁止などをコードで強制する。失敗時はログに理由を残し、無限ループしない。
- **なぜ:** 画像 API は単価が高くなりがち。リトライ地獄は最も起きやすい暴走パターン。

---

## 10. Gemini / OpenAI 混線禁止

- **ルール:** 1 つの処理フローで、設定が OpenAI なのに内部で Gemini クライアントを混在させない。フォールバックが必要なら **明示のフラグとログ** を必須とする。
- **ルール:** 本文生成、画像プロンプト生成、品質チェックは、それぞれ `TEXT_LLM_PROVIDER`、`IMAGE_PROMPT_LLM_PROVIDER`、`QUALITY_CHECK_LLM_PROVIDER` を個別に解決する。本文生成 provider を他用途に暗黙流用しない。
- **ルール:** provider と実際に呼ぶ低レベル関数（例: `openai` → `call_openai_text`）が一致しない場合は、黙って続行せず例外で停止する。
- **なぜ:** 出力品質・データ取り扱い・課金単位が異なる。暗黙のフォールバックはデバッグ不能になる。

---

## 11. 作業完了後は必ず GitHub へ push する

- **ルール:** Codex / Cursor / 人間開発者は、作業完了後に変更をローカルだけで終わらせず、必ず Git に commit し、GitHub へ push する。
- **対象:** 最低限、`docs/*`、`reports/*`、修正コード、テストコード、設定変更、README 変更を push 対象にする。
- **なぜ:** ChatGPT / Cursor / Codex 間で URL 共有できる状態にし、スクリーンショット共有やチャット履歴依存を減らす。作業履歴と引き継ぎ可能性を保つ。

---

## 12. 作業結果は reports/latest_report.md に保存する

- **ルール:** 作業結果の詳細は必ず `reports/latest_report.md` に保存する。必要に応じて `reports/codex_report_YYYYMMDD_HHMM.md` も作成する。
- **含める内容:** 実施した作業、調査内容、修正内容、変更ファイル、テスト結果、発見した問題、未解決事項、次にやるべきこと、ChatGPT へ相談したいこと。
- **なぜ:** チャット上だけで完結させず、レビュー・共有・将来の引き継ぎに使える記録をリポジトリ内へ残す。

---

## 13. 完了報告は URL 共有まで行い、チャットは要約にする

- **ルール:** 作業完了時のチャット報告には、最低限次を含める。  
  - コミット ID  
  - 変更ファイル一覧  
  - GitHub URL  
  - `reports/latest_report.md` の GitHub URL
- **ルール:** 詳細説明は `reports/latest_report.md` に寄せ、チャットでは要約のみ表示する。
- **なぜ:** ChatGPT 側でレビューしやすくし、毎回の長文説明やスクリーンショット共有を減らす。

---

## ドキュメント追記のトリガー

次のイベントがあったら **本ファイル** または `PROJECT_CONTEXT.md` に追記する。

- 新しい Provider や認証方式の追加
- ログフォーマットの変更
- テスト戦略（モック方針）の変更
- GUI と設定ストアのデータモデル変更
- GitHub push / reports 運用ルールの変更

文体・プロンプト・過去バグの教訓は **`PROMPT_HISTORY.md`** へ。
