# プロンプト・ルール・指示の蓄積

**目的:** 重要なプロンプト方針・文体・画像ルール・開発上の禁止事項を、チャット履歴に依存せずリポジトリで共有する。変更があったら **追記** し、日付と一言サマリを残すとよい。

---

## 夜風アカウント文体ルール（yokaze_daily）

- **短文寄り:** 長文説教より、余白のある短い行の積み重ね。
- **読者の側:** 「あなたはダメ」ではなく「そう感じるのは自然」から入る。
- **口語と書き言葉のバランス:** 完全な口語だけ、逆に硬すぎる文章だけは避ける。夜のトーンは **落ち着いた口語** が基準。

**なぜ:** 夜帯は防衛反応が強く、正論・長文は離脱やブロックにつながりやすい。

---

## お兄さん感ルール

- **包容:** 弱さを指摘するのではなく、名前をつけて受け止める（例: 疲れ、焦り、照れ）。
- **少し先を見せる:** 説教ではなく「次の一歩が小さければいい」という視点。
- **距離感:** 馴れ馴れしすぎず、冷たすぎない。過度な絵文字連打はトーンを崩す場合がある。

**なぜ:** 「お兄さん」は権力ではなく **信頼のメタファー**。幼児退行を誘う表現は避け、対等な大人への寄り添いを目指す。

---

## 本音を言語化するルール

- **ラベリング:** 読者がもやっとしていることを 1〜2 語で言語化してから、軽く展開する。
- **断定の避け方:** すべてを断定しない。「〜かもしれない」「〜と感じる人が多い」など余地を残す。
- **自己開示の度合い:** アカウント人格に合わせた軽い自己開示は可。過剰な私小説化は避ける。

**なぜ:** 本音系は外しやすい。**言語化の精度**が価値の中心。

---

## 綺麗なポエム禁止（夜風）

- **避ける:** 連続比喩、抽象語の盛り合わせ、インスタ詩的な改行だらけの美文。
- **代わりに:** 具体的な情景 1 つ、または身体感覚に近い言葉（眠気、胃、肩）を少しだけ。

**なぜ:** ポエム調は「作られたアカウント」感が出て、本音路線の信頼を損ねる。

---

## AI 業務改善アカウントルール（ai_side_business / ai_pickup）

- **中心方針:** 「AI副業ノウハウ」ではなく、非エンジニアが AI で仕事を軽くし、業務改善できる人材を目指す実践発信にする。
- **投稿者の立場:** 成功者・専門家として教えるのではなく、ChatGPT・Codex・Claude・Gemini などを試しながら、自分の作業や投稿生成システムを少しずつ改善している実践者として書く。
- **投稿タイプ比率:** 共感・気づき型 30〜40%、実践記録型 25〜30%、AIツール話題型 15〜20%、実務ノウハウ型 15〜20%、危機感・方向性型 5〜10%、図解向き型 5〜10%。
- **AIツール話題型:** ChatGPT・Claude・Gemini・Codex などを入口にしても、単なるニュース紹介や最強ツール比較で終わらせない。必ず非エンジニアの実務活用、作業の渡し方、業務改善、または Codex での実践記録に着地させる。
- **実践ツール:** 投稿者自身の実践では Cursor ではなく **Codex** を優先して使う。
- **小さなAI活用ヒント:** 投稿が抽象論や考察だけで終わりそうな場合は、最後に AI 活用のヒントを 1 文だけ自然に入れる。例: GPTのプロジェクト機能で入口を分ける、Codexで小さな処理ルールを作る、ChatGPTに業務フローを分解させる、会議メモを次の作業に分ける。答えを出し切らず、「それ気になる」と思える程度に留める。
- **ヒントの制限:** 1投稿につき基本1つ。複数ツールや複数手順を詰め込まない。「〜すべきです」ではなく「〜で試せそう」「〜から始められそう」くらいの柔らかさにする。
- **文体:** X 投稿として、真面目すぎる教材文にしない。少し人間味と軽さを残しつつ、怪しい副業感・成功者風・説教感は避ける。
- **画像判定:** 画像は毎回不要。共感・気づき型、実践記録型、軽い AI ツール話題型は基本 text_only。最後に小さなAI活用ヒントが入っていても、それだけで画像ありにはしない。図解、手順、Before/After、3分類、ロードマップ、チェックリストなど保存価値が明確な場合だけ image。

**なぜ:** 読者の入り口として AI ツール話題は有効だが、ニュース紹介だけでは蓄積価値が弱い。実務の小さな改善と作業分解に戻すことで、note 化したときにも学びとして残る。

## 図解生成ルール

- **結論ファースト:** 上部に結論または比較表の勝者を置く。
- **階層:** 見出し → 小見出し → 箇条書きの順でスキャンしやすく。
- **装飾の抑制:** 意味のないアイコンだらけにしない。装飾は情報のグルーピングにだけ使う。
- **文字サイズ:** スマホで読める下限を決め、それ未満に縮めない（必要なら枚数を増やす）。

**なぜ:** 「図解」と名乗りながら文字が読めない画像はシェアされず、信頼も落ちる。

---

## API を勝手に叩かないルール（プロンプト・運用共通）

- チャット上の推論・下書きでは、**実キーでの呼び出しをデフォルトにしない**。
- 「動作確認したい」ときは、ユーザーが範囲と回数を指定できる形にする。

**なぜ:** エージェントは試行錯誤で呼び出し回数が増えやすい。コストと規約遵守のため明示合意が必要。

---

## 共有・報告の運用ルール

- 作業詳細はチャットに長く出しすぎず、`reports/latest_report.md` に保存する。
- 完了時は commit / GitHub push / GitHub URL 共有まで行う。
- ChatGPT に相談したい観点は report に明記し、URL で渡せる状態にする。

**なぜ:** ChatGPT / Cursor / Codex 間の引き継ぎをしやすくし、毎回同じ運用説明を繰り返さないため。正式ルールは `DEVELOPMENT_RULES.md` を正とする。

---

## GUI 設定一致チェックルール

- 設定を読む場所が複数ある場合は、**読み取りの単一化**を優先してリファクタするか、少なくとも起動時に整合性チェックを入れる。
- 変更 PR では「GUI で変更した値がどの変数に流れ、どの関数が呼ばれるか」を文章か図で示す。

**なぜ:** 設定不整合は再現が難しく、ログがなければ永遠に「疑惑」のままになる。

---

## 品質チェック運用ルール

- **人間レビュー:** 初回テンプレート変更時はサンプル数本を必ず目視。
- **自動チェック:** 禁止語・文字数・必須ハッシュタグの有無など、機械的に判定できるものはスクリプト化。
- **アカウント別:** yokaze_daily と ai_side_business（旧 ai_pickup）でチェックリストを分ける（文体と画像で基準が異なる）。

**なぜ:** 自動化が進むほど、**小さな設定ミスが一斉送信**になる。早期のゲートが必要。

## new_account_daily 文体・画像判断ルール

- **中心方針:** 普通の日常をそのまま報告せず、「少しオシャレで、大人びていて、ほんのり色気や余韻のある日常アカウント」として生成する。
- **投稿比率:** 何気ない日常 1〜2割、オシャレで大人びた日常 4〜6割、かなり大人びた余韻 2〜3割。
- **文体:** 日本語は 2〜4文。日記報告、自己啓発、名言風、過度なポエムを避ける。大人っぽい語彙を使うが、気取りすぎない。
- **品質チェック:** ただの出来事説明・生活記録で終わっていないか、余韻と大人っぽさがあるか、色気が上品で露骨ではないかを見る。
- **Image Need Check:** 文章だけで余韻が完成している場合は `text_only`。夜の部屋、雨、灯り、コーヒー、グラス、カーテンなどの視覚的な空気感が投稿を補強できる場合だけ `image`。
- **画像方針:** 文字なし・人物なし・顔なし・説明要素なし。生活感のあるオシャレな日常背景に限定する。

**なぜ:** 旧方針は生活記録寄りで、X 上で「また読みたい」と思われる雰囲気が弱かったため。

## モックテストルール

- 外部 API はモック。返却 JSON は **実レスポンスに近い形**（フィールド欠落があるとバグを逃す）。
- Provider 切替のテストでは、`provider` が期待値であることと、**誤ったクライアントが選ばれないこと**の両方を検証する。

**なぜ:** モックが簡単すぎると本番だけ落ちる。混線バグは分岐テストで潰す。

**詳細なバグ履歴（原因・修正・テスト・再発防止の全項目）は `BUG_HISTORY.md` に集約する。** 以下は短いメモ用テンプレートである。

| 日付 | 概要 | 原因（推定可） | 対策 |
|------|------|----------------|------|
| （例） | GUI は OpenAI、ログは Gemini | デフォルト分岐の誤り | 設定解決の単一化 + ログ |

**運用:** 再発防止策がコードに入ったら、その PR リンクまたはコミットハッシュを **`BUG_HISTORY.md` の該当エントリ** に併記すると Codex でも追跡しやすい。

## 変更時の追記先クイックガイド

| 変更の種類 | 追記先 |
|------------|--------|
| アカウント別の世界観・文体・画像・禁止事項の固定 | **`ACCOUNT_STYLE_GUIDE.md`**（本ファイルは補助的なプロンプト断片向け） |
| アカウント方針に紐づく短いプロンプト断片・運用メモ | **本ファイル** |
| API・ログ・テスト・GUI と実装の整合 | **`DEVELOPMENT_RULES.md`** / **`PROJECT_CONTEXT.md`** |
| プロジェクトの目的・問題意識・Provider 構成 | **`PROJECT_CONTEXT.md`** |
| 重大バグ・混線・暴走の正式記録 | **`BUG_HISTORY.md`** |
| 作業詳細・調査結果・ChatGPT 共有用メモ | **`reports/latest_report.md`** |

Cursor にだけ書いた指示は **必ずいずれかの docs に昇格**させる。
